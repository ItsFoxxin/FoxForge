# FoxForge 0.4.0 — isolated worker foundation

Base: `dev` merge `8305dc8d2b68d56f5705f9a5a003ac6ef88a4e81`, containing reviewed
0.3.1 commit `aefd096`. Branch: `feature/0.4-worker-foundation`. Release numbering
is **0.4.0**, with subsequent increments such as **0.4.1**, not lettered releases.

This is a tested synthetic execution prototype, not autonomous coding or a
production worker deployment. The production control plane remains planning-only.
No issue, planning approval or `awaiting_human_review` task can dispatch it.

## Implemented boundaries

| Component | Responsibility |
| --- | --- |
| `worker_protocol.py` | Versioned strict JSON, immutable approval scope, bounded messages, Ed25519 signatures; no runtime commands |
| `worker_controller.py` | Operator-approved worker keys, fixture-only authorization, durable attempts/leases, concurrency, ordered result validation and audit in existing SQLite |
| `worker_runtime.py` | Worker key stays outside sandbox; pinned controller verification, durable replay inbox, mock inference, signed checkpoints/tool evidence/results |
| `worker_docker.py` | Trusted worker-host Docker supervisor; fixed launch policy, bounded pipes, deadline/cancellation, container removal and explicit expired-container cleanup |
| `worker_sandbox.py`, `Dockerfile.worker` | Separate non-root Linux process, private tmpfs workspace, registered synthetic tools and tests; no Qwen, Git, credentials or inference network |
| `worker_profiles.py` | Separate version-1 Qwen profiles, operator-selected models, deterministic configuration export and external digest checks; no Qwen invocation |

There is no message broker, listener, daemon, arbitrary shell API, worker registry
service or second task orchestrator. The current transport is a callable/file-sized
signed JSON envelope. The wire contract is language-independent; see
[the protocol specification](WORKER_PROTOCOL.md). Future network transport must
add deployment authentication, routing and cancellation delivery, not replace the
authorization ledger or give models control of these mechanisms.

## Threat model and limits

Assume repository contents, model text, tool output and worker messages are hostile.
An attacker may edit a message, replay an assignment/result, choose an unexpected
path/tool, fabricate JSON, produce unlimited output, consume resources or inject
instructions. Production credentials must never enter execution sandboxes.

Trusted components are the operator, controller configuration/signing key, enrolled
worker supervisor/signing key, reviewed fixture image, Docker daemon and worker
kernel. A registered worker's signature authenticates that supervisor; it is **not**
remote attestation, proof of truthful tests or protection from a compromised worker.
Independent trusted validation against an exact candidate revision is still required
before future publishing. Tool evidence is collected by the fixture broker and
signed outside the container, not generated by a model.

The in-container fixture broker is not a tamper-proof auditor of hostile code.
Arbitrary same-UID code could attack its broker/procfs or fabricate output. Only
reviewed built-in fixtures run here. Before introducing arbitrary repositories,
move trusted tool supervision outside tenant execution and require independent
CI; a signed worker result alone must never approve integration or publishing.

The prototype demonstrates these restrictions on a disposable Docker host:

- UID/GID `11001:11001`, read-only root, dropped Linux capabilities,
  `no-new-privileges`, default Docker seccomp, no mounts or published ports.
- `--network=none`; no keys, provider tokens, App credentials, Docker socket,
  Proxmox access or host filesystem mounts. Only a resolved fixture scope enters stdin.
- One CPU, at most 256 MiB RAM with no additional swap, 32 processes, 128 file
  descriptors, no core dumps, private `/workspace` tmpfs at most 16 MiB and `/tmp`
  tmpfs 4 MiB. File output is capped by `RLIMIT_FSIZE`; combined captured stdout
  and stderr are at most 32 KiB; all artifacts total at most 8 KiB.
- Lease deadline at most 300 seconds, bounded mock requests/tokens, no automatic
  retries; container alarm provides a deadline even if the supervisor disconnects.
- A random supervisor-owned container name, disabled Docker logs, forced removal
  on completion, cancellation or overflow. Workspaces vanish with their container.
- A fixed test command registry, fixed calculator fixture and exact read/write
  paths. There is no model-supplied command string. Runtime configuration is not
  read from the disposable fixture.

Docker shares the worker kernel. It does not contain kernel exploits, hostile
multi-tenant workloads, side channels, compromised images or a privileged Docker
operator. Docker access makes the **supervisor** privileged relative to that host;
use a dedicated disposable worker VM, separate from the production control plane,
before expanding beyond this synthetic test. The planned worker VM, hypervisor
boundary, daemon hardening, disk quotas/retention, egress restrictions and transport
have not been deployed or verified here. No GPU or local inference is assumed.

`worker_demo` intentionally co-locates logical controller and supervisor in a
short-lived **integration harness** for CI. It generates temporary signing keys
in memory; none enter containers or logs. This harness is not the topology to run
on the existing 2-vCPU/4-GB control-plane VM. A real separate worker receives only
its own signing key, pinned controller public key, signed assignments and scope.
It never receives the controller key, App key, controller DB or GitHub write token.

The control-plane image retains `FOXFORGE_CONTROL_PLANE_ONLY=1`. New runtime,
Docker supervisor, cleanup and demo entrypoints reject this mode before effects;
the sandbox runner also rejects it. The allowlisted container CLI is unchanged.
Never unset the flag or mount the host socket to make a worker run there.

## Authorizations, state and recovery

Only a trusted operator can enroll an externally verified worker public key and
authorize an exact `fixture.execute` scope. Self-registration cannot grant trust.
Only the built-in synthetic Git fixture identity/base revision and `quality.assurance`
are supported. IDs are `fixture_*`; ordinary issue task IDs fail validation.
Approval binds task, action, repository ID, base SHA, expiry and a digest of all
parameters, tools, paths, profile, policy version and budgets. Planning approval
and execution approval are never interchangeable.

The controller reuses the schema-1 database and audit table, adding only
`workers_v1`, `worker_attempts_v1` and `worker_events_v1`. Core project/task/approval
records and legacy JSON are not rewritten. Attempts progress through `issued`,
`accepted` and a terminal `succeeded`, `failed`, `cancelled` or `interrupted` state.
Checkpoints report real sandbox milestones, never fabricated percentages.

Signed ordered events must match the immutable assignment digest, worker, attempt,
sequence, live lease and cumulative resource limits. Duplicate or stale results
cannot complete work twice. Cancellation immediately invalidates subsequent
results. A signed cancellation can be validated by the worker; prompt delivery
and acknowledgment over a real transport are future deployment work. Local
supervisor cancellation is exercised in CI. Expired leases become `interrupted`
only through explicit recovery; no uncertain attempt is restarted automatically.

Worker-local SQLite receipts are persisted **before** acknowledging acceptance or
launching a sandbox. Their role is replay prevention, not authorization. A crash,
lost acknowledgment or cancellation retains the receipt. Requests are accounted
before dispatch; unknown/interrupted allocations are not reused by a retry.
Mock `tokens=200` is a deterministic synthetic budget charge, not measured provider
usage. Real inference and provider accounting remain deferred.

The controller validates artifact names, sizes and hashes, writes bounded artifacts
under `artifacts/<fixture-task>/<attempt>/` before committing success, and refuses
symlinks/overwrites. Failed transactions can leave inspectable orphan artifacts;
they never authorize another run. Backup verification now includes worker table
counts and worker artifact presence. Use the existing quiesced SQLite/artifact
backup procedure. The separate worker inbox also needs archival preservation if
a real worker is later provisioned; do not erase receipts to retry uncertain work.

## Run the disposable prototype

Ordinary Python unit tests require neither Docker nor inference:

```bash
python -m pip install '.[dev]'
python -m pytest -q
```

For the optional integration prototype, use a reviewed commit on a **disposable
Linux Docker host**, not the production control plane. Docker Engine is an explicit
prerequisite; no service installation or VM configuration is performed by FoxForge.
The image uses the same pinned Python/Debian base as 0.3.1. Review/build it first:

```bash
docker build -f Dockerfile.worker -t foxforge-worker:0.4.0 .
python -m foxforge.worker_demo --state-dir /tmp/foxforge-fixture-NEW --scenario success
```

`/tmp/foxforge-fixture-NEW` is an **example new directory**; choose a new path for
each run. Existing state directories are refused. The supervisor resolves the
reviewed local image tag to an immutable image ID before launching; it never pulls
an arbitrary model-selected image. Successful output reports `succeeded` plus the
attempt identity; SQLite and validation artifacts remain in the disposable directory.
The harness uses synthetic operator ID 1, not a GitHub identity or production grant.

Other registered scenarios are `readonly-denial`, `unavailable`, `output`, `deadline`,
`memory`, `disk`, `network` and `processes`. These intentionally fail or interrupt
within the sandbox. They are fixed synthetic probes, not arbitrary administration
tools. Run the complete real-container checks with:

```bash
python ci/worker_smoke.py
python -m foxforge.worker_demo --cleanup-expired
```

Cleanup removes only containers carrying `foxforge.prototype=true` with an expired
timestamp. It never deletes unrelated containers, host workspaces or task history.
After a lost supervisor, wait for the container deadline, inspect the ledger, then
perform cleanup. New work requires a new explicit authorization and new identity.

## Qwen profiles and compatibility

The six legacy templates, settings and PowerShell installer remain unchanged,
with release-hash regression tests. Their local model IDs are legacy deployment
configuration, not assumptions made by the new worker profiles.

New profiles are centrally defined in `worker_profiles.py`, version 1, and are
exported to a **new staging directory**. Models must be explicit operator-approved
IDs: `inherit`, `fast`, unknown IDs and injected YAML are rejected. Read-only
profiles have no edit/write/shell tools. Implementation/testing profiles have
bounded-purpose edit tools but **no shell**; validation belongs to the broker.
Helper and reporter profiles remain available but are never mandatory new stages.

Example, replacing the model placeholder with an actually approved gateway model:

```bash
python -m foxforge.worker_profiles --output /tmp/foxforge-reviewer-NEW \
  --role reviewer --model 'openai:REPLACE_APPROVED_MODEL_ID' \
  --approved-model 'openai:REPLACE_APPROVED_MODEL_ID'
```

This writes inert frontmatter and settings, prints a configuration SHA256, and
does not contact a model or install over `.qwen`. Pin that hash outside the staging
directory. `verify_configuration` compares the exact expected bytes, names, model,
tools, mode and hash; modified settings, extra hooks/files and symlinks fail closed.
No mutable manifest in the same directory is accepted as authority. A future
worker installer will materialize only this reviewed configuration inside its
isolated runtime; this release does not launch it against repositories.

Official Qwen sources were checked at commit
[`34769f9`](https://github.com/QwenLM/qwen-code/commit/34769f9d41a1ea253a000285f3c32e60fac6fb26)
on 2026-10-26. The
[subagent reference](https://github.com/QwenLM/qwen-code/blob/34769f9d41a1ea253a000285f3c32e60fac6fb26/docs/users/features/sub-agents.md)
supports `model`, `approvalMode` and `tools` frontmatter. The
[settings implementation](https://github.com/QwenLM/qwen-code/blob/34769f9d41a1ea253a000285f3c32e60fac6fb26/packages/cli/src/config/settings.ts)
defines settings version 4. The
[configuration reference](https://github.com/QwenLM/qwen-code/blob/34769f9d41a1ea253a000285f3c32e60fac6fb26/docs/users/configuration/settings.md)
marks `tools.core` deprecated and distinguishes auto-approval from tool restriction.
New profiles use no deprecated `tools.core` configuration. Do not replace the
legacy runner's core-tool flags with `permissions.allow`: they are not equivalent.
Legacy invocation remains unchanged until actual runtime parity is demonstrated.
Parent approval modes can override agent modes; none of these settings provide
OS isolation. A real Qwen binary/version, providers, permissions and tool behavior
have not been exercised by this mock milestone.

## Consolidation and next releases

| Classification | Existing components | Migration gate |
| --- | --- | --- |
| Retain as controller authority | `control_plane.py`, `capabilities.py`, `actor_authorization.py`, planning schema/provider | Preserve planning-only gates and existing task history |
| Reuse/extract carefully | `git_manager.py`, `process.py`, `test_runner.py`, `state_validator.py`, `security.py` | Reuse validation/parsing/timeout invariants; avoid unbounded output or host execution in new paths |
| Worker-only execution | Repository tests, edits, subprocesses and eventually checkout operations | Real worker OS boundary, trusted configuration, cancellation, budget and independent validation parity |
| Qwen-specific adapter | `agent_runner.py`, Qwen prompt/frontmatter/launcher logic | Pin/test real Qwen in the isolated worker; universal protocol stays model/runtime neutral |
| Deprecate after parity | Mandatory six-stage `coordinator.py`, legacy `issue_intake.py`/watch dispatch and Windows worker launcher | Explicit execution approvals, equivalent regression coverage, historical access and rollback |
| Eventually remove after approved migration | Duplicated generic per-project agent copies and superseded legacy dispatch | Operator inventory/customization review; no automatic deletion or silent history import |

Keep Python: no benchmark demonstrates a control-plane language bottleneck.
Bounded JSON allows future Go/Rust supervisors without changing authorization.
0.4.1 or later may add an authenticated remote transport and reviewed live runtime
adapter. Full autonomous coding, live issue dispatch, arbitrary shells, real Qwen
execution, GitHub writes, publishing, Proxmox operations, infrastructure remediation,
deployment, Heretic/model modification, paid fallback and dashboards are deferred.

Rollback stops prototype activity and retains its SQLite/inbox/artifacts for
inspection. The 0.3.1 control-plane deployment and legacy assets need no migration
to run this disposable harness. Old readers ignore additive worker tables, but
cannot validate worker histories; archive/verify with 0.4.0 before any rollback.
Do not copy worker credentials or the demo into the production Compose stack.

## Validation boundaries

Unit tests cover registration/trust, signature forgery, strict schemas, replay,
lease expiry, cancellation, stale results, tool/path scope, cumulative budgets,
malformed/oversized data, artifact integrity/backup, profile tampering, preserved
legacy assets and control-plane execution rejection. No unit test needs Docker.
Hosted Linux CI additionally builds the actual sandbox and exercises real fixture
tests, resource probes, fresh-workspace isolation, cancellation and cleanup.
CI remains validation → Linux/Windows tests → distribution → containers.

Container smoke success is evidence for these disposable configurations, not
certification of a live Proxmox VM or safe hostile multi-tenant execution. No paid
API, real provider, Qwen model, production credential or live service is used.
